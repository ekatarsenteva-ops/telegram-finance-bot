# Требования к ПО: ИИ-ассистент для учета финансов (ФИНАЛЬНАЯ ВЕРСИЯ)

## 1. Введение и цели

**Цель продукта:** Создать надежное решение для учета финансов двух объектов (школа языков и недвижимость) с поддержкой трёх типов операций: свободные приходы, плановые платежи, групповые расходы с отслеживанием возврата денег от участников.

**Основной пользователь:** Собственник объектов (начальный этап).

**Ключевая ценность:**
- Минимизация ручного ввода (естественный язык в Telegram);
- Автоматический учёт взаимозачётов;
- Отслеживание долгов по групповым расходам;
- Синхронизация в Google Sheets для анализа.

---

## 2. Функциональные требования

### 2.1. Модуль ввода данных (Telegram-бот)

**FR-1.1:** Система должна принимать текстовые и голосовые сообщения от авторизованного пользователя.

**FR-1.2:** Система должна поддерживать команды: `/start`, `/help`, `/export [период]`, `/balance`, `/debts`.

### 2.2. Модуль AI (Claude API)

**FR-2.1 (STT):** Автоматическая транскрибация голоса в текст (90%+ точность на русском).

**FR-2.2 (Извлечение сущностей):** ИИ должен парсить:
- Обязательные: тип операции, сумма, валюта (по умолчанию RUB), дата (по умолчанию сегодня), контрагент, объект
- Категория (из справочника, привязанного к объекту)
- **[НОВОЕ]** Тип платежа:
  - **Приход** ("пришло X от контрагента") → свободный платёж, добавляется на баланс объекта
  - **Входящий платёж** ("аренда за месяц", "ежемесячный взнос") → может быть привязан к взаимозачётам
  - **Групповой расход** ("разделить на N", "поровну на участников") → создаёт должников с отслеживанием возврата
- Признаки взаимозачёта ("зачет в аренду")

**FR-2.3 (Диалог уточнения):** Один вопрос за раз, пока не заполнены все поля.

**FR-2.4 (Подтверждение):** Карточка со всеми данными перед записью в БД.

### 2.3. Модуль хранения данных

**FR-3.1:** Реляционная БД (PostgreSQL / Supabase) как источник правды.

**FR-3.2:** Справочники: объекты, категории (привязаны к объектам), контрагенты.

**FR-3.3:** Таблицы:
- `transactions` (все операции)
- `expense_participants` (участники групповых расходов с отслеживанием возврата)
- `counterparty_offsets` (взаимозачёты)

**FR-3.4:** История парсинга (raw_ai_log) для аудита.

### 2.4. Модуль отчётности

**FR-4.1:** Экспорт за период: `/export YYYY-MM-DD:YYYY-MM-DD` → .xlsx

**FR-4.2:** Баланс контрагентов: `/balance` → таблица текущих должников/кредиторов

**FR-4.3:** Долги по групповым расходам: `/debts` → кто и сколько должен вернуть

**FR-4.4:** Синхронизация Google Sheets (витрина, read-only, обновление в реальном времени)

### 2.5. Управление пользователями

**FR-5.1:** Идентификация по telegram_id.

**FR-5.2:** Архитектура поддерживает RBAC для расширения на несколько пользователей.

---

## 3. Нефункциональные требования

**NFR-1. Производительность:** Отклик на текст 3-5 сек, на голос 7-10 сек.

**NFR-2. Масштабируемость:** До 50 операций/день, архитектура готова к линейному расширению.

**NFR-3. Надежность:** Ежедневные бэкапы Supabase, механизм повторных попыток для Sheets API.

**NFR-4. Безопасность:** Telegram-аутентификация, HTTPS, API-ключи в переменных окружения.

**NFR-5. Сопровождаемость:** Промпты в конфигах, логирование всех парсингов ИИ.

---

## 4. Интеграции

| Сервис | Назначение | Требование |
|--------|-----------|-----------|
| Telegram Bot API | Основной интерфейс | Webhook, встроенные кнопки |
| Claude API | Парсинг операций | JSON Mode, русский язык |
| STT (Yandex/Whisper) | Расшифровка голоса | 2-3 сек отклик |
| Google Sheets API | Витрина для просмотра | Service Account, read-only синхронизация |
| Supabase/PostgreSQL | Источник правды | HTTPS, бэкапы, JSON для raw_ai_log |

---

## 5. Ограничения

- Взаимозачёты: на старте базовая поддержка
- Групповые расходы: разовое деление с отслеживанием возврата (на is_paid флаге)
- Sheets: витрина, read-only, двусторонняя синхронизация на будущее
- Банковская интеграция: не в MVP
- Один пользователь на старте
- Только русский язык на старте
- Никаких уведомлений/напоминаний

## 6. User Story (обновлены)

### US-1: Ввод свободного прихода

**Как** координатор, **я хочу** отправить сообщение "пришло сейчас 15 тыс руб от Пети", **чтобы** быстро зафиксировать поступление денег.

**Критерии приемки:**
- Бот парсит: тип (приход), сумма, валюта, контрагент, дата (сегодня);
- Если не указан объект → спрашивает "Для какого объекта?";
- Показывает карточку: "Приход 15 000₽ от Пети, Объект 1, 2025-08-01";
- После подтверждения записывает в БД.

### US-2: Ввод входящего платежа (с возможной привязкой к взаимозачётам)

**Как** координатор, **я хочу** ввести "арендатор недвижимости внес арендную плату за месяц 50 тыс", **чтобы** зафиксировать плановый платеж и автоматически применить если есть открытые взаимозачёты.

**Критерии приемки:**
- Бот определяет, что это "входящий платёж" (слова "платеж", "внес", "перевел");
- Парсит: сумма, контрагент, дата, объект;
- Если у контрагента есть открытые взаимозачёты → показывает "На счёте открытых взаимозачётов: 15 000₽. Применить к этому платежу?";
- При "Да" → платёж уменьшается, зачёт переводится в "применён";
- Записывает операцию (платёж со скидкой или без, в зависимости от выбора).

### US-3: Групповой расход с отслеживанием возврата

**Как** координатор, **я хочу** отправить "организовали пикник, расход 9 тыс руб, делим поровну между Ивой, Марией, Петром", **чтобы** система автоматически распределила долги и позволила отслеживать возврат денег.

**Критерии приемки:**
- Бот парсит: тип (расход), сумма, количество участников, дата, объект;
- Если имена не указаны → спрашивает "Кто участники?";
- Показывает карточку: "Расход 9 000₽ на пикник, Школа. Долги: Ива 3 000, Мария 3 000, Петр 3 000";
- После подтверждения создает записи в `expense_participants` с флагом `is_paid = false`;
- При возврате денег пользователь может обновить статус: "Петр вернул свою долю" → `is_paid = true` для Петра;
- Команда `/debts` показывает актуальный список должников.

### US-4: Баланс контрагентов и взаимозачёты

**Как** координатор, **я хочу** видеть баланс всех контрагентов (кто сколько должен, кому должен), **чтобы** понимать расчёты.

**Критерии приемки:**
- Команда `/balance` выводит таблицу:
  - Контрагент | Сумма взаимозачётов | Статус открытых долгов
- Команда `/debts` выводит таблицу:
  - Контрагент | Сумма долга | Участие в каких расходах | Кол-во вернуло/не вернуло

### US-5: Экспорт операций

**Как** координатор, **я хочу** выгрузить все операции за период в Excel, **чтобы** провести анализ.

**Критерии приемки:**
- Команда `/export 2025-08-01:2025-08-31` генерирует .xlsx;
- Колонки: Дата, Объект, Тип, Сумма, Валюта, Категория, Контрагент, Статус (приход/платёж/расход), Кто внес;
- Если есть групповые расходы → отдельный лист с деталями по участникам и их статусам возврата.

### US-6: Справочники категорий

**Как** администратор, **я хочу** управлять категориями для каждого объекта, **чтобы** система корректно классифицировала операции.

**Критерии приемки:**
- При добавлении категории указывается объект и тип (приход/расход);
- ИИ использует справочник при парсинге, предлагает ближайшую категорию;
- Справочники видны в Google Sheets (лист "Справочники").

## 7. Примеры команд

```

/debts                                      # Долги по групповым расходам

```

## 8. Примеры естественного ввода

```
"Пришло 15000 рублей от Пети"
→ Приход, 15000 RUB, Петя, сегодня

"Арендатор внес аренду за август, 50 тыс"
→ Входящий платёж, 50000 RUB, Арендатор, сегодня, может быть привязано к взаимозачётам

"Купили материал для школы, 6 тыс, зачет в аренду"
→ Расход, 6000 RUB, Взаимозачёт, категория "Материалы"

"Организовали пикник в школе, 9 тыс, делим поровну между Ивой, Марией, Петром"
→ Групповой расход, 9000, 3 участника, школа

"Петр вернул свою долю за пикник"
→ Обновление статуса: is_paid = true для Петра
```
